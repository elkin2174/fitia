# HU 1 — Registro con correo institucional

Documentación de la implementación backend de la HU 1 del MVP FITIA: qué se construyó, cómo funciona, cómo se probó y cómo probarlo a mano.

> Estado: implementado y probado (99 pruebas pasando en Python 3.14 local y 3.11 en Docker). Sin commit todavía.

---

## 1. Qué hace la HU 1

Un estudiante se registra con correo `@correounivalle.edu.co`, apodo, contraseña y programa académico, y acepta el consentimiento de datos (HU 8). La cuenta queda **pendiente de verificación**; se envía un enlace al correo. Al abrir el enlace (el frontend hace un `POST`), la cuenta se verifica, se crea una sesión y la API responde `next: "onboarding"` (diagnóstico inicial, HU 4).

Flujo:

```
GET  /api/v1/programs                  → lista de programas (formulario)
POST /api/v1/auth/register             → 201 pending_verification  (+ correo en segundo plano)
        ↓ el usuario abre {FRONTEND}/verificar-correo?token=...
POST /api/v1/auth/verify-email         → 200 {user, next:"onboarding"} + cookie fitia_session
POST /api/v1/auth/resend-verification  → 202 siempre (si el enlace venció o se perdió)
```

Todas las mutaciones exigen el encabezado `X-Requested-With: fitia`.

## 3. Cómo funciona

### 3.1 Registro (`POST /api/v1/auth/register`)

Cuerpo: `{ nickname, email, password, program_code, accepted_terms }`. Orden de proceso en `AuthService.register`:

1. **Rate limit** por IP y por correo (hash del correo, nunca el correo en claro) → 429 `RATE_LIMITED`.
2. **Normalización**: correo `trim + lower` (AC-1-5); apodo `trim`.
3. **Validación acumulada** (todos los errores juntos en `fields`, 422 `VALIDATION_ERROR`):
   - `NICKNAME_LENGTH` — apodo vacío o fuera de 3–20 (AC-1-9)
   - `PROGRAM_REQUIRED` — ausente, vacío o inexistente en BD (AC-1-4)
   - `TERMS_REQUIRED` — `accepted_terms` distinto de `true` (AC-1-6)
   - `WEAK_PASSWORD` — menos de 8 caracteres (supuesto S-02); `PASSWORD_TOO_LONG` — más de 128
   - `INVALID_EMAIL` — formato inválido o más de un `@`
4. **Dominio exacto**: lo que hay tras el único `@` debe ser igual a `correounivalle.edu.co`. Rechaza `x@correounivalle.edu.co.evil.com`, subdominios y prefijos → 422 `DOMAIN_NOT_ALLOWED` con el mensaje "Solo se admiten correos @correounivalle.edu.co" (AC-1-2).
5. **Unicidad** → 409 `EMAIL_EXISTS` (AC-1-3). Además, si dos peticiones compiten y la BD lanza `IntegrityError` por `users_email_key`, también se devuelve 409.
6. **Una sola transacción**: crea `user` (`email_verified_at = NULL`), `consent` (versión `CONSENT_TEXT_VERSION` + fecha) y `email_verification_tokens` (solo el hash SHA-256; `expires_at = now + 24 h`). Argon2id se calcula en un threadpool para no bloquear el event loop.
7. **Después del commit** se encola el correo con `BackgroundTasks` (NFR-01). Si el proveedor falla, se registra el error y el registro sigue siendo exitoso.

Respuesta: `201 {"status": "pending_verification"}`. No devuelve id, hash ni token.

### 3.2 Verificación (`POST /api/v1/auth/verify-email`)

- La consumición del token es **atómica**: un único `UPDATE ... WHERE token_hash=? AND used_at IS NULL AND expires_at > now RETURNING user_id`. Así dos peticiones simultáneas con el mismo token no pueden usarlo ambas (NFR-09, un solo uso).
- Si no devuelve fila (no existe, vencido o usado) → 410 `TOKEN_EXPIRED_OR_USED` con mensaje que invita a solicitar uno nuevo (AC-1-8).
- Si es válido, en la misma transacción: fija `email_verified_at`, crea la sesión (`issue_session`: token opaco, solo se guarda el hash, expira en `SESSION_TTL_DAYS`) y responde `200 {user:{id,nickname,program:{code,name}}, next:"onboarding"}` (AC-1-7).
- Cookie `fitia_session`: `HttpOnly`, `Secure` según `COOKIE_SECURE`, `SameSite=Lax`, `Path=/`, 30 días. Encabezado `Cache-Control: no-store`. El correo no aparece en la respuesta.
- `issue_session` queda reutilizable para el login (HU 2).

El enlace del correo apunta a una **página del frontend** (`{FRONTEND_BASE_URL}/verificar-correo?token=...`), que debe hacer el `POST`. Nunca se consume el token con `GET` (ADR-08), para que los escáneres de correo no lo gasten.

### 3.3 Reenvío (`POST /api/v1/auth/resend-verification`)

Cuerpo `{ email }`. Responde **siempre 202 con el mismo cuerpo**, exista o no la cuenta, sea institucional o no, o venga vacío (evita enumeración). Si hay una cuenta pendiente: marca como usados los tokens previos sin usar, crea uno nuevo y lo envía en segundo plano. Una cuenta ya verificada no recibe correo. El rate limit se aplica igual exista o no la cuenta.

### 3.4 Programas (`GET /api/v1/programs`)

Pública, devuelve `[{code, name}]` ordenado por nombre con collation ICU `es-x-icu` (el orden coincide entre Postgres local, CI y Supabase).

### 3.5 Base de datos

Migración `0001_hu1_auth_schema` (extensión `citext`):

| Tabla | Notas |
|---|---|
| `academic_programs` | `code` PK, `name` |
| `users` | `email citext UNIQUE`, `role DEFAULT 'student'`, `email_verified_at` NULL |
| `email_verification_tokens` | `token_hash UNIQUE`, `expires_at`, `used_at` |
| `consents` | `text_version`, `accepted_at` (auditable, NFR-19) |
| `sessions` | `token_hash UNIQUE`, `expires_at`, `last_seen_at` |

CHECK en `users`: dominio `email ~ '^[^@\s]+@correounivalle\.edu\.co$'` (NFR-07), `char_length(nickname) BETWEEN 3 AND 20`, `role IN ('student','monitor')`. Todas las FK hacia `users` son `ON DELETE CASCADE` (lo necesitará la HU 3).

### 3.6 Infraestructura transversal

- **Error uniforme**: `{"error": {"code", "message", "fields": [{"field","code"}]}}`, también para 422 de Pydantic, 404/405 y errores no controlados (500 genérico, sin detalles).
- **CSRF**: toda mutación bajo `/api/v1` sin `X-Requested-With: fitia` → 403 `CSRF_HEADER_MISSING`.
- **Rate limit**: ventana deslizante en memoria (por proceso). Por defecto 30 por IP y 5 por correo cada 15 min (`RATE_LIMIT_*`). Devuelve `Retry-After`.
- **Logs**: JSON estructurado; los campos `email`, `password`, `token` salen como `[REDACTED]` y un filtro enmascara correos, `token=` y hashes Argon2 si se colaran en un mensaje.
- **Pooler de Supabase**: `statement_cache_size=0` y nombres de prepared statements únicos. Las URLs `postgresql://...?sslmode=` se convierten al formato de asyncpg.
- **Mailer**: `ConsoleMailer` (imprime el enlace en stdout, solo local) y `HttpMailer` (API compatible con Resend). Con `ENV=production` y `MAIL_PROVIDER=console` la app **no arranca**, para que el token no acabe en los logs de Render.

## 4. Cómo se hicieron las pruebas

**Stack**: pytest + pytest-asyncio + `httpx.AsyncClient` con `ASGITransport` (sin servidor real) contra un **Postgres real** (no mocks de BD).

**Entorno de prueba** (`tests/conftest.py`):
- Una vez por sesión: se borra y recrea el schema `public` de `fitia_test`, se aplican las **migraciones reales de Alembic** y se carga el seed. Así las pruebas validan también la migración y los CHECK.
- Tras cada test: `TRUNCATE users CASCADE`.
- Se inyectan por `dependency_overrides`: sesión de BD, `FrozenClock` (reloj controlado), `FakeMailer` (captura envíos), `Settings` de prueba y un `RateLimiter` nuevo por test.
- `FakeMailer.last_token()` extrae el token del enlace capturado, igual que lo haría el usuario.

**Técnicas destacadas**:
- *Vencimiento*: `clock.advance(24h + 1s)` → 410; `24h − 1s` → 200.
- *Condición de carrera*: se parchea `email_exists` para que devuelva `False` aunque el correo ya exista, forzando que sea la restricción UNIQUE de la BD la que dispare el 409.
- *NFR-01*: un middleware ASGI de prueba marca cuándo se envió el cuerpo final de la respuesta; el `FakeMailer` anota ese estado cuando se invoca. Se verifica que el correo se envía **después** de entregar la respuesta.
- *Almacenamiento seguro*: se lee la BD directamente para comprobar prefijo `$argon2id$`, que el token guardado es solo el SHA-256 y que el hash de la cookie coincide con la sesión.
- *CHECK de BD*: `INSERT` directo con `@gmail.com` o apodo de 2 caracteres debe fallar con `ck_users_email_domain` / `ck_users_nickname_length`.

**Resultados**: 99 pruebas (unitarias + integración) pasan en Python 3.14 local y en `python:3.11-slim` (Docker, mismas versiones fijadas de `requirements.txt`). Además se hizo un smoke test manual con uvicorn real (registro en ~72 ms, verificación, reutilización del token → 410).

## 5. Cómo probarlo manualmente

### 5.1 Levantar el entorno

Desde la raíz del repo. Si ya tienes un Postgres local en 5432 (es tu caso), usa el puerto 5433 para el contenedor:

```bash
POSTGRES_PORT=5433 docker compose up -d db
cd apps/api
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env
```

Edita `apps/api/.env` para que coincida con el puerto elegido:

```
DATABASE_URL=postgresql+asyncpg://postgres:postgres@localhost:5433/fitia_db
DATABASE_URL_DIRECT=postgresql+asyncpg://postgres:postgres@localhost:5433/fitia_db
TEST_DATABASE_URL=postgresql+asyncpg://postgres:postgres@localhost:5433/fitia_test
COOKIE_SECURE=false
MAIL_PROVIDER=console
```

Migrar, cargar programas y arrancar:

```bash
.venv/bin/alembic upgrade head
.venv/bin/python -m seeds.load_academic_programs
.venv/bin/uvicorn app.main:app --reload --proxy-headers
```

Swagger en http://localhost:8000/docs (ojo: desde Swagger las mutaciones darán 403 salvo que agregues el encabezado `X-Requested-With`; es más fácil con curl).

### 5.2 Recorrido con curl

```bash
B=http://localhost:8000/api/v1
H=(-H "X-Requested-With: fitia" -H "Content-Type: application/json")

# 1. Programas
curl -s $B/programs

# 2. Registro (AC-1-1, AC-1-5: nota los espacios y mayúsculas)
curl -s -i "${H[@]}" $B/auth/register -d '{
  "nickname":"Pantera","email":"  Ana.Gomez@CorreoUnivalle.edu.co ",
  "password":"contrasena-segura","program_code":"ING-SIS","accepted_terms":true}'
# → 201 {"status":"pending_verification"}
# En la terminal de uvicorn aparece el correo con el enlace; copia el valor de token=...

# 3. Verificar (AC-1-7)
TOKEN=pega_aqui_el_token
curl -s -i "${H[@]}" $B/auth/verify-email -d "{\"token\":\"$TOKEN\"}"
# → 200, Set-Cookie: fitia_session=...; HttpOnly; SameSite=lax, Cache-Control: no-store, "next":"onboarding"

# 4. Reusar el mismo token (AC-1-8)
curl -s "${H[@]}" $B/auth/verify-email -d "{\"token\":\"$TOKEN\"}"
# → 410 TOKEN_EXPIRED_OR_USED
```

### 5.3 Casos de error a probar

| Qué probar | Petición | Esperado |
|---|---|---|
| Otro dominio (AC-1-2) | email `x@gmail.com` | 422 `DOMAIN_NOT_ALLOWED` |
| Sufijo malicioso | `x@correounivalle.edu.co.evil.com` | 422 `DOMAIN_NOT_ALLOWED` |
| Varios `@` | `a@b@correounivalle.edu.co` | 422 `VALIDATION_ERROR` + `INVALID_EMAIL` |
| Correo repetido (AC-1-3) | registrar dos veces | 409 `EMAIL_EXISTS` |
| Sin programa (AC-1-4) | omitir `program_code` | 422 campo `program_code` |
| Sin consentimiento (AC-1-6) | `"accepted_terms": false` | 422 campo `accepted_terms` |
| Apodo corto/largo (AC-1-9) | `"ab"` o 21 caracteres | 422 campo `nickname` ("entre 3 y 20") |
| Varios errores a la vez | `-d '{}'` | 422 con todos los `fields` |
| Sin CSRF | quitar `X-Requested-With` | 403 `CSRF_HEADER_MISSING` |
| Reenvío | `POST /auth/resend-verification` con `{"email":"..."}` | 202 siempre; llega un enlace nuevo y el anterior da 410 |
| Reenvío a correo inexistente | `{"email":"nadie@correounivalle.edu.co"}` | 202 idéntico, sin correo |
| Rate limit | 6 reenvíos seguidos al mismo correo | el 6.º da 429 con `Retry-After` |

Para reiniciar el contador de rate limit (está en memoria) reinicia uvicorn.

## 6. Supuestos tomados

1. **S-02**: contraseña mínima de 8 caracteres; máximo 128 (`PASSWORD_TOO_LONG`) para evitar abuso del costo de Argon2.
2. Los errores de campo se acumulan primero; el dominio se valida después. Un `@gmail.com` con apodo inválido reporta primero el apodo.
3. Los **códigos de programa son provisionales** (`ING-SIS`, `MED`…). Hay que reemplazarlos por los oficiales de Univalle y completar la lista (comentario en `seeds/academic_programs.json`).
4. La collation `es-x-icu` existe en las imágenes oficiales de Postgres; **no se verificó en Supabase**.
5. Rate limit en memoria y por proceso (con varias instancias en Render habría que usar un almacén compartido). Límite por IP alto a propósito porque muchos estudiantes comparten IP del campus. Para obtener la IP real detrás de Render/Vercel, uvicorn debe correr con `--proxy-headers`.
6. `HttpMailer` usa una API compatible con Resend (`MAIL_API_URL`); el proveedor definitivo no está decidido.
7. `accepted_terms` debe ser booleano JSON; `"true"` como texto da error de validación con código `INVALID`.
8. El registro de un correo existente devuelve 409 (lo exige AC-1-3), por lo que ahí sí es posible saber si una cuenta existe; el reenvío no lo revela.
9. `COOKIE_SECURE` es `true` por defecto; en local sobre HTTP debe ponerse en `false` (el `.env.example` ya lo hace).

## 7. Pendiente / fuera de alcance

Login (HU 2), logout y eliminación de cuenta (HU 3), onboarding (HU 4), perfil y ranking. Falta también la página del frontend `/verificar-correo` que haga el `POST`, y una versión final del texto de consentimiento (`CONSENT_TEXT_VERSION`) cuando se defina la HU 8.
